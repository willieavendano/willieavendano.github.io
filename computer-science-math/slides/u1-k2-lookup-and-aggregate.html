Lookup & Aggregate

Concept Deck II

VLOOKUP applied · SUMIF / AVERAGEIF · charts that tell the truth

Second concept deck of Cornerstone I. VLOOKUP itself is not new — students built it in Toolbox Week 3. Today it gets pointed at a real reference table with a Source column, and then we add the second move: aggregation. The chart section is not decoration; the kit rubric grades Communication explicitly, and a truncated axis is a correctness failure, not a style choice.

Why this matters

Two moves do most of the work in every model this year

Fetch a fact from a reference table, and summarise many rows into one number. Everything else is layout.

Fetch a fact
VLOOKUP — search a reference table and return one value from that row
Summarise many
SUMIF / AVERAGEIF — collapse many rows into a single number

Master these two and the rest is layout.

This claim is literal, not motivational: Unit 2's car loan, Unit 3's budget, and Unit 4's portfolio all reuse lookup-plus-aggregate in some form. Students who leave today able to build both moves on their own have the engine of the whole year.

VLOOKUP · Recap

The call, briefly

=VLOOKUP(lookup_value, table_array, col_index, FALSE)
  • lookup_value — the Food name to find
  • table_array — the Food Table, locked with $
  • col_index — which column to return
  • FALSE — exact match, always

Introduced in Toolbox Week 3 — today we point it at the tracker.

VLOOKUP · Applied

Lookup, then multiply by servings

In the Daily Log, row 2 holds a food in C2 and a serving count in D2:

=VLOOKUP($C2,'Food Table'!$A$2:$G$20,3,FALSE)*$D2

Read it left to right

Find C2 in the Food Table, return column 3 (Calories), then multiply by the servings in D2.

The lookup returns one serving; the multiplication makes it your serving.

Students constantly forget the second half — they return calories for one serving and never multiply by D2, so every total is silently low. Make them say the sentence out loud: "lookup, then multiply by servings." Column 3 is Calories; if they later want protein, it is col_index 4.

VLOOKUP · The $ Lock

Why the range is absolute

The $ signs freeze the table so the formula can be filled down hundreds of rows without sliding off it.

$C2
locked column, free row — every row looks up its own food
$A$2:$G$20
locked both — the table stays put for every row

Leave off the $ and row 20 reads a different range than row 2.

The absolute-reference idea is the same one from Unit 0 Week 2. The failure is quiet: without the lock the formula still computes on row 2 and only breaks several rows later, so students cannot see the cause. Have them fill down and spot-check the bottom row before trusting the column.

A Second Lookup

Return the Source, too

Same machine, different col_index. The Source is column 7:

=VLOOKUP($C2,'Food Table'!$A$2:$G$20,7,FALSE)

Now the log knows where each number came from, and the Source cell takes its color from the class key.

One lookup for the value, one for the trust level.

This is how the color coding actually happens: the color is driven by the looked-up source text, not typed by hand. Some students will hard-code the source color per row; push them to derive it so that correcting the Food Table updates the whole log. Conditional formatting keyed on the source text is the clean version.

VLOOKUP · Staying Honest

When the food is not in the table

=IFERROR(VLOOKUP(…), "not in table")

A misspelled name returns #N/A. Wrapping the lookup keeps the sheet readable and tells the reader the truth: this food has no source yet.

Do not hide the miss — label it.

Warn against the tempting shortcut: wrapping in IFERROR with a guess like 0. That converts "I do not know" into "this food has zero calories" and corrupts every aggregate downstream. The text label is the honest choice; it is visible and it demands a fix.

The Three Classic Failures

How VLOOKUP breaks

ProblemWhat you seeThe fix
Misspelled name#N/Amatch the Food Table spelling exactly
col_index off by onethe right row, the wrong numbercount the columns; A is 1
range_lookup blank / TRUEa close-but-wrong match, often with no erroralways type FALSE

Two of the three fail loudly. The col_index and TRUE errors lie quietly.

The quiet failures are the dangerous ones: a wrong col_index returns a plausible number (serving size instead of calories), and TRUE can match "Apple" to "Apple Pie". Teach the habit of reading the formula aloud — value, table, column number, FALSE — before trusting any result.

Part Two

Aggregate

Many rows in. One number out.

SUMIF

Total calories for one day

=SUMIF(date_range, this_date, calories_range) adds the calories only where the date matches.

=SUMIF('Daily Log'!$A$2:$A$200, $A2, 'Daily Log'!$E$2:$E$200)

Range to check, the criterion, then the range to add.

Emphasize the shape: one range is tested, a different range is summed. Students who have only used SUM find this disorienting at first. The date criterion points at a Weekly Summary cell so the formula can be filled down and each row totals its own day.

→ 105 + 330 + 206 = 641 kcal

One formula per day — fill it down the Weekly Summary.

Note that the 330 is chicken at two servings times 165 — a good place to re-check that the day's individual rows already did their lookup-times-servings multiplication. SUMIF should never do the multiplying; it only adds finished numbers.

AVERAGEIF

Average calories per day

Once each day has a total, average across the days that have data:

=AVERAGEIF($C$2:$C$15,"<>",$D$2:$D$15)

The criterion "<>" means non-blank — it ignores days you never logged.

Why not AVERAGE()

AVERAGE() would divide by the empty days and drag your average down.

The conceptual point: an average over what you collected, not over every calendar slot. If a student logged 10 of 14 days, dividing by 14 invents four days of eating nothing. AVERAGEIF with "<>" only counts the days that actually have a total.

The Dashboard Pipeline

From the log to one number

Daily Log → SUMIF per day → AVERAGEIF across days → Target vs Actual → one chart

Daily Log

Weekly Summary

Target vs Actual
subtract the target from the day's total
One chart
answer the question the dashboard raised
Walk the pipeline as a chain: each stage feeds the next, and a mistake upstream contaminates everything downstream. If the Daily Log's lookups are wrong, the sum is wrong, the average is wrong, and the chart is confidently wrong. This is why we verify each stage before building the next.

Part Three

Charts that tell the truth

A chart is a sentence, not decoration.

The kit rubric grades Communication, and a misleading chart fails that criterion the same way a wrong formula fails Model Correctness. Frame chart honesty as a math standard, not an aesthetic preference — that is what gets students to take it seriously.

Chart Choice

The question picks the chart

Bar
compare categories — this day vs that day, this food vs that food
Line
show a trend over time — calories across two weeks
Scatter
show a relationship — protein vs calories

Pick the chart that answers your question, not the one that looks best.

Make students name the question first, then choose. The common failure is a pie chart of daily calories — pie slices imply parts of a whole, and days are not parts of a whole. The other is a line chart through unordered categories like food names, which invents a trend that does not exist.

Honest Axes

Three rules that separate honest from misleading

Start at zero
bar charts that start mid-axis exaggerate every difference
Label with units
axes read kcal, g, or dates — never bare numbers
Title the question
“Which days did I go over target?” not “My Chart”

A clipped axis can make a 5% difference look like a cliff.

This is the same dogma as labels travelling with the math, applied to a chart: an axis without units is a number without a unit. The zero rule applies to bar charts specifically — line charts of a quantity that does not start at zero are sometimes legitimate, so do not overgeneralize.

Worked Chart

Which days did I go over my calorie target?

Bar chart, one bar per day, y-axis in kcal starting at zero, with the target drawn as a line at 2,000 kcal.

What the chart says

Monday, Wednesday, and Saturday rise above the target line; the other four days sit below it.

Mark the over-target days so the reader's eye lands on the answer.

Show the honest version on screen and then, briefly, the dishonest one — same data with the axis starting at 1,800 so every bar looks like a crisis. Ask the class which chart makes a claim the data supports. That comparison does more than any rule read aloud.

From Chart to Insight

Describing is not understanding

Weak

“My chart shows my daily calories for the week.”

Strong

“I go over target on days I skip breakfast — but this is one week, and one busy weekend could explain it.”

A strong insight makes a claim the data supports, then names the caveat that would change it.

The weak example describes the artifact; the strong one makes a claim and immediately qualifies it. Require both halves in the write-up: the supported claim and the caveat. A claim with no caveat overreaches; a caveat with no claim is just describing the chart again.

Two moves, three chart rules

  • IFERROR keeps a missing food honest instead of showing #N/A.
